<objective>
## Goal
`pwvault breach update` downloads the Have I Been Pwned Pwned Passwords list into a compact local store outside the vault folder, and `pwvault check` lists entries whose passwords are breached, reused or weak, with no network access during the check.

## Purpose
A daily-driver password manager has to say which passwords need changing. Doing it offline means no password, hash or hash prefix ever leaves the machine because of a check.

## Output
- Store format, builder and lookup in pwvault.py (`$XDG_CACHE_HOME/pwvault/pwned/`, default `~/.cache/pwvault/pwned/`)
- CLI: `pwvault breach update`, `pwvault breach import FILE`, `pwvault breach status`, `pwvault check`
- `check_vault()` engine returning findings, reused by the GUI in 08-02
- tests/test_breach.py (no network), README and CHANGELOG lines
</objective>

## Source
HIBP no longer publishes a single download file. The list is the 16^5 = 1,048,576 range files at
`https://api.pwnedpasswords.com/range/{5 hex}` (free, no key). Each line is `SUFFIX:COUNT` with a
35-hex-character SHA-1 suffix. Fetching every range reveals nothing about the user's passwords.
Send a generic `User-Agent: pwvault-manager/<version>` (HIBP rejects requests without one). No padding
header (padding only matters for single lookups); skip any `:0` lines anyway.

## Store (`pwned/` directory)
- `hashes.bin`: for each range in order, its suffixes sorted, each stored as the first 6 bytes (12 hex
  chars) of the 35-char suffix. With the 20-bit prefix that is 68 bits per hash; false-match odds are
  about N / 2^68 per password (~1 in 10^11 for 2 billion hashes).
- `index.bin`: 1,048,577 little-endian uint64 record offsets (range r is records index[r]..index[r+1]), ~8 MB.
- `meta.json`: format version, source, hash count, completed date.
- Lookup: SHA-1 the password (uppercase hex), read the two index entries, read that range's slice
  (a few KB), bisect. Never loads hashes.bin into memory. Open files read-only.
- Store missing, partial or with mismatched sizes → `VaultError` naming `pwvault breach update`.

## Build (update and import share one writer)
- Writes `hashes.bin.partial` + `index.partial` + `progress` in the store dir, appending ranges in
  order. Downloads in batches of 4096 ranges over a thread pool (16 workers), appends each finished
  batch, fsyncs, records progress. Interrupted → next `update` resumes from the last finished batch.
- Each range response validated: every line `^[0-9A-F]{35}:\d+$`, suffixes strictly increasing; on
  failure or HTTP error retry with backoff (5 tries), then stop with an error (progress kept).
- Finish: write meta, fsync, rename partial files over the live ones (a lookup during an update
  keeps using the old complete store).
- Before starting, `shutil.disk_usage` must show at least 16 GB free (6 bytes × ~2.6 billion
  headroom); otherwise stop with the number needed.
- `import FILE`: build the same store from a `HASH:COUNT` text file sorted by hash (the output of
  HIBP's PwnedPasswordsDownloader), streamed line by line, same validation. Lets offline machines
  and tests build a store without the network.
- `update` on an existing complete store rebuilds into partial files and swaps at the end.

## Check
`check_vault(vault, store) -> list[Finding]`, where Finding = (entry, issues ⊂ {"breached",
"reused", "weak"}, reused_with: list of other entries). Entries in the recycle bin and entries with
an empty password are skipped. Reused = same password string in 2+ checked entries. Weak =
`strength()` label "weak". Breached skipped (with a note) when no store exists; reused and weak
still reported. Passwords are never printed or logged.

<acceptance_criteria>

## AC-1: Store build and lookup
```gherkin
Given a set of range responses (or a sorted HASH:COUNT file) containing the SHA-1 of "password1"
When `pwvault breach update` (or `pwvault breach import FILE`) completes
Then the store exists under $XDG_CACHE_HOME/pwvault/pwned/ (default ~/.cache/pwvault/pwned/), outside the vault folder
And a lookup of "password1" is found, a password not in the list is not found, and a hash sharing only the 5-hex prefix is not found
And a lookup reads only that range's slice, never the whole file
```

## AC-2: Interrupted or bad downloads never leave a broken store
```gherkin
Given an update interrupted after some batches, or a range response that is malformed or out of order
When the update stops and is run again
Then the earlier complete store (if any) is still used for lookups until the new one finishes
And the rerun resumes from the last finished batch instead of starting over
And a malformed response is retried and, if it stays bad, the update fails with an error naming the range
```

## AC-3: `pwvault check` reports breached, reused and weak passwords
```gherkin
Given a vault with a breached password, two entries sharing one password, a weak password, a strong unique one, an empty password, and a breached one in the recycle bin
When the user runs `pwvault check`
Then it lists each flagged entry (title, username, group) with its issues, names the entries a reused password is shared with, and prints a total
And the strong, empty and recycle-bin entries are not listed
And no password appears in the output
```

## AC-4: No network during the check, clear message without a store
```gherkin
Given network access is made impossible (socket creation raises)
When `pwvault check` runs with a store present, and again with none
Then both runs succeed without opening a socket
And without a store it reports reused and weak entries and says to run `pwvault breach update` for breached ones
```

## AC-5: Real download (human-verify)
```gherkin
Given network access and at least 16 GB free
When the user runs `pwvault breach update` against the real HIBP API (interrupting once with Ctrl+C and rerunning), then `pwvault check` on their vault
Then the update completes and resumes, `pwvault breach status` shows the hash count and date, and the check finishes in seconds
```
