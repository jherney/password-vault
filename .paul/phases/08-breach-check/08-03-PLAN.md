<design>
## Decisions (user, 2026-11-05)
- Integrity: SHA-256 of index.bin in meta.json, verified on open; CRC32 per range in crc.bin, verified on each lookup. No whole-file hash of hashes.bin (minutes per open).
- Format 1 stores are reported as outdated ("rebuild with `pwvault breach update`"); no migration, since no real store exists yet (08-01 AC-5 deferred).
- Fix both leftovers in this plan.

## Store format 2
- `crc.bin`: PWNED_RANGES little-endian uint32, `zlib.crc32` of each range's stored records (empty range = crc32(b"") = 0). 4 MB.
- `meta.json`: adds `"index_sha256"`; `"format": 2`.
- Build: `_BreachBuild.append` also appends each range's CRC to crc.bin, fsynced with the batch, before the index entries are written (the index stays the resume point). Resume truncates crc.bin to `done * 4`. `finish` hashes index.bin (8 MB, streamed) into meta.
- Open: format must be 2 (format 1 → outdated message); crc.bin size must be PWNED_RANGES*4; SHA-256 of index.bin must match meta. Mismatch → `VaultError(BreachStore.DAMAGED)`.
- Lookup: after reading range r, compare crc32(data) with crc.bin[r] (one extra 4-byte pread); mismatch → VaultError(DAMAGED). `check_vault` lets it propagate, so the CLI and GUI show the damaged state rather than a wrong answer. The 08-01 "one range read" property becomes three small reads (16 B index, 4 B crc, the range).

## Leftovers
- GUI note: show the command as plain text with non-breaking spaces (`pwvault breach update`, no backticks), via a small display step in CheckDialog; the shared VaultError text used by the CLI stays as is.
- `breach import`: free space needed = min(PWNED_MIN_FREE, size of the input file + 64 MB for index and crc), since the store is far smaller than its HASH:COUNT text. `breach update` keeps 20 GB.

## /cso
`/cso --diff --base 67a13d7` (last main commit before Phase 8) after Tasks 1–2, so it reviews the final code. Critical/high findings are fixed in this plan with a test; medium/low are fixed if small, else recorded in STATE Deferred Issues. Results go in the summary and PROJECT.md's Security review metric at phase transition.
</design>

<acceptance_criteria>

## AC-1: Corruption is reported, not silently missed
```gherkin
Given a breach list built by `breach import` or `breach update`
When one index offset is changed so a populated range looks empty, or one byte of a range's records is flipped, or crc.bin or meta's index hash is altered
Then opening the store, or looking up a password in the affected range, raises the "damaged — run `pwvault breach update`" error
And `pwvault check` and the GUI report show the breach list as damaged instead of listing fewer breaches
And an intact store still finds and misses exactly as before
```

## AC-2: Build, resume and format
```gherkin
Given a download interrupted mid-batch and resumed, or a download compared with an import of the same hashes
When the store finishes
Then crc.bin, index.bin and hashes.bin are byte-identical between the two, and every range's CRC matches its records
And a format 1 store is reported as outdated with the `breach update` hint
```

## AC-3: Leftovers
```gherkin
Given no breach list, when the GUI report opens, then its note names pwvault breach update without backticks and the command is never split across lines
Given 3 GB free and a small HASH:COUNT file, when `breach import` runs, then it succeeds; and when free space is below the file size + 64 MB, it is refused with the amount needed
And `breach update` still requires 20 GB free
```

```gherkin
Given Tasks 1–3 are done
When `/cso --diff --base 67a13d7` runs on Phase 8
Then the report is saved, every finding is triaged, critical/high findings are fixed with a test, and the rest are fixed or recorded with a reason
```
