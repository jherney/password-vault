<objective>
## Goal
Publish pwvault 1.3.0 to PyPI from a tagged GitHub Actions run using trusted publishing, so no API token is stored anywhere.

## Purpose
The core value is a vault you control; distribution is the last Phase 5 goal: `pip install <name>` from PyPI, and tag v1.3.0.

## Output
- `.github/workflows/publish.yml`: build, test, and publish on `v*` tags, with trusted publishing
- pyproject.toml: distribution name decided by the user
- Git tag `v1.3.0` and a published release on PyPI
</objective>

<acceptance_criteria>

## AC-1: Distribution name is free to publish under
```gherkin
Given the chosen distribution name
When the publish workflow runs
Then the project is created on PyPI under that name (not the existing "pwvault" project owned by someone else)
```

## AC-2: Publish uses trusted publishing, with no stored token
```gherkin
Given publish.yml
When it runs on a v* tag
Then the job has id-token: write, uses environment "pypi", and passes no password or API token
```

## AC-3: Only tested artifacts are published
```gherkin
Given a v* tag
When publish.yml runs
Then the tests job passes before the publish job starts, and the publish job uploads the sdist and wheel that the build job produced
```

## AC-4: The published release installs and runs
```gherkin
Given the release is on PyPI
When a clean venv runs `pip install <name>==1.3.0` and then `pwvault --version`
Then it prints "pwvault 1.3.0"
```

<task type="checkpoint:decision" gate="blocking">
  <decision>Distribution name on PyPI. "pwvault" is already taken by another project (0.1.1, "A local encrypted password manager"), so this release cannot use it.</decision>
  <context>The import name and commands can stay `pwvault` and `pwvault-gui`; only the PyPI distribution name changes. The name is public and hard to change after publishing.</context>
  <options>
    <option id="option-a">
      <name>pwvault-kdbx (recommended)</name>
      <pros>Says what it is (KeePass vault); clearly distinct from the other project</pros>
      <cons>Longer to type in pip</cons>
    </option>
    <option id="option-b">
      <name>pwvault-manager</name>
      <pros>Short and generic</pros>
      <cons>Generic name; more likely to be taken or confused with others</cons>
    </option>
  </options>
  <resume-signal>Select: option-a or option-b (or give another name; check it is free at https://pypi.org/project/NAME/)</resume-signal>
</task>

<task type="auto">
  <name>Task 1: Set the distribution name and write the publish workflow</name>
  <files>pyproject.toml, .github/workflows/publish.yml, README.md</files>
  <action>
    - Set `name` in pyproject.toml to the chosen distribution name. Leave `pwvault` as the module and command name.
    - Write publish.yml triggered on `push: tags: ["v*"]`, with `permissions: contents: read` at the top. Three jobs: `test` (reuse the tests.yml steps, lock file install from 05-01), `build` (needs test; `python -m build`; upload dist/ as an artifact), `publish` (needs build; `environment: pypi`; `permissions: id-token: write`; uses pypa/gh-action-pypi-publish with no password input).
    - Pin every action to a full commit SHA with the tag in a comment, the same policy as tests.yml (F-11). Look up SHAs with `gh api repos/OWNER/REPO/commits/TAG` rather than guessing.
    - Add `build` to the dev install instructions in README only if needed; avoid adding it to requirements.txt.
    - Avoid: a PyPI API token secret; publishing on every push; publishing from a job that did not depend on the tests.
  </action>
  <verify>Parse publish.yml with python yaml; check the publish job has id-token: write, environment: pypi, no password input; `grep -n "uses:" .github/workflows/publish.yml` shows only SHA-pinned actions; `python -m build` produces a sdist and wheel with the chosen name in the filenames.</verify>
  <done>AC-1 (name chosen and free) and AC-2 satisfied by the config; AC-3 satisfied by the job graph.</done>
</task>

<task type="checkpoint:human-action" gate="blocking">

  <why>PyPI's trusted-publisher setup is a web step on the account; it cannot be done from this repo.</why>
