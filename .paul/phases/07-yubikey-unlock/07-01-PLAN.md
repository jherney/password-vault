<objective>
## Goal
A vault can be protected by password and/or key file **plus a YubiKey HMAC-SHA1 challenge-response slot**, derived exactly as KeePassXC 2.8 does for KDBX 4, so the same vault opens in both apps with the same key. CLI: `--yubikey SLOT[:SERIAL]` on every command that unlocks, `init`/`passwd` can add or remove it. GUI support is plan 07-02.

## Purpose
A second factor that malware can't copy off the disk, the biggest remaining gap against KeePassXC for daily use, without a custom vault format.

## Output
- A `MasterKey` value (password, key file, YubiKey slot) used by every load and save path
- Challenge-response derivation and an optional YubiKey driver (`yubikey-manager`, extra `[yubikey]`)
- CLI options, clear errors, tests including KeePassXC's own YubiKey test vault
</objective>

## Research done while planning (2026-11-05)
KeePassXC 2.8.0 `src/keys/CompositeKey.cpp` (`rawKey`, `transform`, `challenge`) and `YubiKeyInterface*.cpp`, checked by a working proof:
- KDBX 4 with Argon2: raw key = SHA256( SHA256(password) ‖ keyfile-key ‖ SHA256(response) ); the challenge is the KDF seed (Argon2 salt, 32 bytes, header `kdf_parameters['S']`); response = 20-byte HMAC-SHA1 from the key. Then Argon2 as usual. Without a YubiKey nothing is appended (normal vaults unchanged).
- The YubiKey computes HMAC-SHA1(secret, challenge) over the unpadded challenge (KeePassXC pads to 64 bytes for transport; the key strips it). Known answer from KeePassXC's TestCli.cpp: secret `1ce30fd78d20dcfa40b50c18779afb0f02288db7`, challenge `CLITest` → `a23b9400be479a30a9eb509b85565b6b3025b48e`.
- Proof: with that emulated secret, password `a`, and the derivation above, pykeepass opens KeePassXC's `tests/data/YubiKeyProtectedPasswords.kdbx` via `transformed_key=` and lists `entry1`, `entry2` (as KeePassXC's test expects).
- pykeepass keeps the KDF salt when `save(transformed_key=...)` is used, so routine saves keep working with the same response; a new salt (create, re-key) must be set before challenging the key.

```gherkin

When I `passwd` to add, change or remove the YubiKey (with or without changing the password)
Then the vault opens only with the new credentials, and old-key backups are purged as for any re-key (crash-safe marker still works)
And a vault with a key file + YubiKey and no password works
```

## AC-3: Every unlock path takes the YubiKey
```gherkin
Given a YubiKey-protected vault

And backups made before a YubiKey was added still restore only if they open with the current credentials (unchanged rule)
```

<boundaries>

## DO NOT CHANGE
- Derivation for vaults without a YubiKey (byte-identical files and behavior)
- Merge engine rules; `Vault._write()` locking/backup; re-key purge semantics
- Vault format: nothing YubiKey-specific is stored in the file (KeePassXC stores nothing either); which slot to use is the user's to give

## SCOPE LIMITS
- GUI (unlock screen, change master key, merge dialog) is plan 07-02
- No YubiKey support for KDBX 3 / AES-KDF vaults (refused with a clear message)
- No programming of YubiKey slots from pwvault (use ykman)
- No FIDO2/hmac-secret, OnlyKey or other drivers in this plan
