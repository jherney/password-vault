<objective>
## Goal
An entry can store a TOTP (2FA) secret in the standard `otp` attribute that KeePassXC uses. `pwvault totp QUERY` copies the current code, `pwvault totp QUERY --set` / `--clear` manage the secret, and the GUI shows a live code with a countdown next to the password. Codes come from a stdlib RFC 6238 generator (SHA-1/256/512, 6–10 digits, any period, Steam codes) checked against the RFC test vectors. Entries that KeePassXC created, including ones that use its older field formats, produce the same codes here.

## Purpose
Core value: "one encrypted local vault … still open it in KeePass-compatible apps." 2FA secrets that already live in a KeePassXC vault are currently invisible in pwvault, and secrets added here should work in KeePassXC. This removes the main reason to keep a second app open for logins.

## Output
- `pwvault.py`: TOTP parsing and generation, `otp` handling in `Vault.add_entry` / `update_entry` (with history), the `totp` CLI subcommand, a line in `get`
- `pwvault_gui.py`: TOTP field in the entry dialog; live code, countdown and Copy in the detail panel; Ctrl+T
- `tests/test_totp.py`: new tests
- `README.md`: TOTP section, CLI table row, Features bullet
</objective>

## Key facts established during planning
- pykeepass 4.2.0 has `entry.otp`, a getter/setter for the `otp` string field (protected when created). `"otp"` is in pykeepass's `reserved_keys`, so `entry.delete_custom_property("otp")` refuses. Clearing it means removing the `<String>` element whose `Key` is `otp` from `entry._element`, just as `delete_custom_property` does internally.
- `update_entry()` and `restore_history()` loop over `Vault.FIELDS` with `getattr`/`setattr`. History versions are `Entry` objects with `.otp`, so restoring an old version restores its TOTP.
- Formats KeePassXC reads (and which pwvault must read the same way):
  1. `otp` = `otpauth://totp/<label>?secret=<BASE32>&period=30&digits=6&issuer=<x>[&algorithm=SHA1|SHA256|SHA512][&encoder=steam]`. This is what KeePassXC writes.
  2. `otp` = KeeOtp style `key=<BASE32>&step=30&size=6[&otpHashMode=Sha256]`
  3. Legacy KeeTrayTOTP: string fields `TOTP Seed` (base32) + `TOTP Settings` = `"<period>;<digits>"`, or `"<period>;S"` for Steam. `TOTP Seed` without settings means 30;6.
- Steam codes: an RFC 4226 31-bit truncated value turned into 5 characters from `23456789BCDFGHJKMNPQRTVWXY` (take `n % 26` five times, dividing by 26 after each).
- No KeePassXC, oathtool or phone authenticator on this machine. Interop is checked with RFC vectors, sample entries in KeePassXC's formats, and a human checkpoint against the user's phone.
- GUI shortcuts already in use: Ctrl+C (password), Ctrl+B (username), Ctrl+N, Ctrl+F, Ctrl+L. Ctrl+T is free and is KeePassXC's "copy TOTP".

<acceptance_criteria>

## AC-1: Codes match RFC 6238
```gherkin
Given the RFC 6238 Appendix B secrets and times (59, 1111111109, 1111111111, 1234567890, 2000000000, 20000000000)
When codes are generated with SHA-1, SHA-256 and SHA-512 at 8 digits, 30 s period
Then every code equals the published value
And 6-digit codes are the last 6 digits of the same values
And a Steam code at counter 0 for "12345678901234567890" equals the 5 characters derived from RFC 4226's truncated value 1284755224
```

## AC-2: KeePassXC's formats are read the same way
```gherkin
Given entries whose TOTP is stored as an otpauth:// URI (with and without algorithm, digits, period, encoder=steam), as KeeOtp "key=…&step=…&size=…", or as legacy "TOTP Seed" + "TOTP Settings" (including "30;S")
When pwvault reads them
Then it uses the same secret, algorithm, digits, period and Steam encoding KeePassXC would
And `otp` wins when both `otp` and the legacy fields are present
And an unreadable value (bad base32, otpauth://hotp, digits outside 6–10, period ≤ 0, unknown algorithm) raises a VaultError that names the problem, never a traceback
```

## AC-3: Setting and clearing a secret
```gherkin
Given an entry
When I set its TOTP to an otpauth://totp URI
Then that URI is stored in `otp` unchanged, as a protected field
When I set it to a bare base32 secret (any case, spaces allowed, as sites display them)
Then `otp` holds `otpauth://totp/<title>:<username>?secret=<SECRET>&period=30&digits=6&issuer=<title>` (URL-encoded), the form KeePassXC writes
When I set or clear it on an entry that has legacy TOTP Seed/Settings fields
Then those legacy fields are removed so only one secret remains
And each change adds a history version (restoring that version brings the old TOTP back)
And clearing it removes the `otp` field entirely; it doesn't leave an empty one
And an invalid secret is refused before anything changes
```

## AC-4: CLI
```gherkin
Given a vault with an entry that has a TOTP secret
When I run `pwvault totp QUERY`
Then the current code is copied to the clipboard (cleared like a password) and I'm told how many seconds it stays valid
When I add --show
Then the code is printed instead (formatted "123 456"), and the secret never is
When I run `pwvault totp QUERY --set`
Then I'm asked for the secret or URI with hidden input, it's validated, the vault is saved, and the current code is shown as confirmation
When I run `pwvault totp QUERY --clear`
Then I'm asked to confirm, and the secret is removed and saved
And `pwvault totp QUERY` on an entry without TOTP exits with a clear error
And `pwvault get` prints a "TOTP:" line ("set — `pwvault totp …`") only for entries that have one; output for other entries is unchanged
```

## AC-5: GUI
```gherkin
Given the GUI with an entry that has a TOTP secret selected
Then the detail panel shows a "ONE-TIME CODE" row with the current code and the seconds remaining, updated every second, plus a Copy button
And Ctrl+T (or double-clicking the code) copies the current code, with the clipboard cleared like a password
And the countdown timer stops when another entry is selected, the vault locks or the detail panel is rebuilt (no timers left running, no errors after lock)
And an entry with an unreadable TOTP shows a muted "unreadable TOTP settings" note instead of a code
When I add or edit an entry
Then a masked "TOTP" field (secret or otpauth:// URI, with Show) lets me set, change or clear it
And an invalid value shows an inline error and saves nothing
And editing other fields of an entry with legacy TOTP fields, without touching the TOTP field, leaves its TOTP storage exactly as it was
```

  <files>pwvault.py, tests/test_totp.py</files>
  <action>
    In pwvault.py, add a "totp" section after the password generator (stdlib only: hmac, hashlib, base64, struct, urllib.parse, time):
    - A small frozen dataclass `Totp(secret: bytes, digits=6, period=30, algorithm="SHA1", steam=False)`.
    - `parse_totp(text: str) -> Totp` for otpauth://totp URIs and KeeOtp `key=…` strings. Base32: strip spaces and `-`, uppercase, add `=` padding, decode with `base64.b32decode`, and refuse an empty result. Names: SHA1/SHA256/SHA512, case-insensitive; KeeOtp's `Sha256` maps the same way. Steam: `encoder=steam` (case-insensitive) sets steam=True, digits=5. Errors raise VaultError: "TOTP secret isn't valid base32", "HOTP (counter-based) codes aren't supported", "TOTP digits must be 6–10", "TOTP period must be a positive number of seconds", "unknown TOTP algorithm X".
    - `entry_totp(entry) -> Totp | None`: `entry.otp` first, then legacy `TOTP Seed` + `TOTP Settings` ("P;D" or "P;S"; missing settings = 30;6). None if neither field exists. Unparseable values raise VaultError.
    - `totp_code(t: Totp, now: float | None = None) -> tuple[str, int]`: the code and the seconds left in its period. Standard codes use RFC 4226 dynamic truncation, then `% 10**digits`, zero-padded. Steam codes use the 31-bit value and 5 characters from the Steam alphabet.
    - `normalize_totp(text, title, username) -> str`: if the text starts with `otpauth://`, validate it with parse_totp and return it stripped but otherwise unchanged. Otherwise treat it as a bare base32 secret and build the otpauth URI described in AC-3 with `urllib.parse.quote`, keeping `:` between title and username in the label; an empty title falls back to "pwvault". Validate the result by parsing it.
    - Vault integration: add `"otp"` to `Vault.FIELDS`, so `update_entry` detects the change, archives history and `restore_history` brings it back. In the setattr loop, for `otp`, write a non-empty value with `entry.otp = value`, and remove an empty one with a helper `_remove_string_field(entry, key)` that deletes the `<String>` element whose `Key` text equals key. pykeepass's `delete_custom_property` refuses `otp` because it's a reserved key, and it uses an XPath built from the key; don't build XPath from strings, iterate over `entry._element.findall("String")` instead. When `otp` changes, also remove `TOTP Seed` and `TOTP Settings`. Add `otp=""` to `add_entry()` and set it when non-empty.
    - Normalization stays with the callers (CLI and GUI call `normalize_totp` before update_entry/add_entry), so `restore_history` writes old values back byte for byte.
    Avoid: storing the secret anywhere other than the protected `otp` field; printing or logging secrets; `time.time()` inside tests without passing `now`.

    tests/test_totp.py (reuse `Base` from test_pwvault):
    - All 18 RFC 6238 Appendix B vectors (SHA-1 seed "12345678901234567890", SHA-256 the 32-byte seed, SHA-512 the 64-byte seed, as raw bytes in `Totp`), 6-digit variants, the seconds-left value, and the Steam vector from AC-1.
    - parse_totp/entry_totp cases for each AC-2 format, the `otp`-over-legacy precedence, and every error message.
    - normalize_totp: a bare secret with spaces and lowercase letters; title/username containing `:`, `&`, spaces and non-ASCII characters; an otpauth URI passed through unchanged; an invalid one refused.
    - Vault: set → save → reopen keeps the URI and the field is protected; clear removes the field (check the element is gone); history plus restore_history round trip; legacy fields are removed when `otp` is set; editing the title alone leaves legacy fields untouched; KeePassXC-style entries made with `set_custom_property` (legacy) and `entry.otp` (URI) produce the expected codes.

- No QR-code scanning or image import
- No TOTP in CSV import/export yet (LastPass `totp`, 1Password `OTPAuth`, Bitwarden `login_totp`): log as a deferred item
- No reading of KeePass 2's native `TimeOtp-*` fields: deferred
- No new runtime dependencies (stdlib only)
