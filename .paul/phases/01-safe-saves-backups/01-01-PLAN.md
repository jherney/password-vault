<objective>
## Goal
Every vault save first keeps a copy of the previous vault file (the last 10 are kept). `pwvault backup list` and `pwvault backup restore` bring an old version back. Fault-injection tests prove that a failed or interrupted save leaves the vault and its backups intact.

## Purpose
Core value is "one encrypted local vault I control". The only copy of every password is that one file, so losing it to a bad save, a bad edit or a bad import is the worst failure this app can have. This phase comes first because every later phase (TOTP, GUI, release) saves the vault, and it should do so with a safety net.

## Output
- `pwvault.py`: backup-on-save inside `Vault.save()`, pruning, purge after a re-key, restore function, `backup` CLI subcommand
- `pwvault_gui.py`: change-password dialog mentions that old backups were removed
- `tests/test_backups.py`: new tests

## Key facts established during planning
- Every save path (CLI commands, GUI `App.save()`, GUI create, `migrate_legacy`) goes through `Vault.save()`. Backups belong there and nowhere else.
- `Vault.save()` already holds an exclusive `flock` on `<vault>.lock` and has already read the on-disk bytes into `current` for its conflict check. The backup reuses those bytes under the same lock, so there is no extra read and no race.
- `write_private()` is already atomic (temp file, fsync, `os.replace`, mode 0600) and resolves symlinks.
- `transformed_key is None` after `create` and after `rekey`. A re-key is the case where `current` exists.
</context>

<acceptance_criteria>

## AC-1: Backup before every save
```gherkin
Given an existing vault file on disk
When any change is saved (CLI or GUI)
Then the previous file contents are written, byte for byte, to <vault-name>.backups/ next to the real vault file before the vault is replaced
And the backup file and directory are owner-only (0600 / 0700)
And a brand-new vault (first save, nothing on disk) creates no backup
```

## AC-2: Only the newest 10 backups are kept
```gherkin
Given 10 backups already exist
When the vault is saved again
Then a new backup is added and the oldest is removed, leaving exactly 10
And files in the backup directory that don't match the backup name pattern are never touched
```

## AC-3: A failed backup blocks the save
```gherkin
Given the backup cannot be written (e.g. an OSError while writing it)
When the vault is saved
Then the save raises an error, the vault file is unchanged, and no partial temp files are left behind
```

## AC-4: Interrupted saves never corrupt the vault
```gherkin
Given an existing vault with known contents
When a save fails partway (serialization error, an error while writing the new vault, or an error at os.replace)
Then the vault file still holds its previous bytes and opens with the same credentials
And the in-memory conflict check still matches the file on disk (a retry doesn't falsely report "changed by another program")
```

## AC-5: List and restore backups from the CLI
```gherkin
Given a vault with several backups
When I run `pwvault backup list`
Then I see each backup numbered newest first, with its timestamp and size
When I run `pwvault backup restore N` and enter the master password (and key file, if used)
Then the backup is checked to open with those credentials before anything changes
And the current vault is itself backed up first, then replaced by the backup's bytes
And a backup that doesn't open with the given credentials is refused with a clear error, and nothing changes
```

## AC-6: Re-key purges old-key backups
```gherkin
Given a vault with backups made under the old master key
When `pwvault passwd` (or the GUI change-password dialog) saves the re-keyed vault
And the new vault file is confirmed to open with the new key
Then every backup in the backup directory is deleted
And the CLI prints how many old-key backups were removed (the GUI shows the same notice)
And if the re-keyed save fails, no backups are deleted
```

  <name>Task 1: Backup, prune and re-key purge inside Vault.save()</name>
  <files>pwvault.py, tests/test_backups.py</files>
  <action>
    In pwvault.py:
    - Add the constant `BACKUP_KEEP = 10` next to `HISTORY_MAX`.
    - Add `backup_dir(path) -> Path`, which returns `<realpath parent>/<realpath name>.backups`. Resolve the real path the same way `Vault.save()` does, so a symlinked vault keeps its backups next to the real file.
    - Name backups `<stem>-<UTC YYYYmmddTHHMMSS.ffffff>.kdbx`, so that sorting by name sorts by age. Add `list_backups(path) -> list[Path]` (newest first; only names matching that pattern) for the CLI to reuse.
    - In `Vault.save()`, inside the existing lock and after the conflict check passes: if `current is not None`, create the backup directory (mode 0700) and call `write_private(backup_dir / name, current)` BEFORE `write_private(target, blob)`. Any error from the backup propagates, so the save does not happen (AC-3).
    - After the vault write succeeds, prune: delete matching backups beyond `BACKUP_KEEP`, oldest first. A pruning failure must not fail a save that has already succeeded. Catch OSError per file and continue.
    - Re-key purge: record in `rekey()` that the key changed (e.g. `self._rekeyed = True`). In `save()`, once the existing `transformed_key` re-derivation succeeds (that proves the new file opens with the new key), delete every backup in the directory if `_rekeyed` is set, and store the count in a field such as `self.purged_backups` so the caller can report it. Then clear `_rekeyed`. If anything before that point raises, nothing is purged (AC-6). Use plain `unlink`: the backups are encrypted, and overwriting is meaningless on btrfs/SSD. Say so in a comment.
    - Keep the existing comments and style. Do not change `write_private()`'s behavior.
    Avoid: backing up outside the lock (race with the GUI); reading the file a second time; backing up from `self.disk_blob` (use `current`, the bytes actually on disk).

    In tests/test_backups.py (reuse `Base` from test_pwvault, as test_keyfile_regression_1 does):
    - First save of a new vault makes no backup; the second save makes 1 whose bytes equal the previous file; check permissions.
    - 12 saves leave exactly 10 backups; a stray file in the directory survives.
    - Backup write failure (patch `write_private` to raise only for paths in the backup directory) → VaultError/OSError, vault bytes unchanged, no `.vault.kdbx-*` temp files left.
    - Re-key then save → backups purged, `purged_backups` reported; re-key with a failed save (patch to raise) → backups still present.
